# 試點：由規則書生成規則測試（1822 第 4 章，2026-11-21）

## 目的
檢驗「規則 → 可執行、帶規則編號的測試 → 自動找出引擎與規則書的差異」是否可行，對應 Nippon／1822 開發中最花人手的「逐條規則人手驗證」。這是初步試點，不是完整實驗。

## 材料
- `henry930/1822`（公開，9 月 24 日的早期 Python 引擎 + `rules.pdf` 44 頁 + 164 個手寫 pytest）。注意：這不是 Mac 上後來的 TypeScript 偽代碼圖版本，那版本這次連不到。
- 規則書抽出約 372 條葉層規則（與專案文檔的 378 接近；雙欄排版令抽取不完全）。

## 基線（現有手寫測試）
- 164 個測試全部通過。
- 測試內明確引用規則編號的只有 13 條（約 3.5%）；第 4 章 75 條中 3 條。注意：這低估真實覆蓋，因為不少測試測了某規則但沒寫編號（例如銀行池 50% 上限）。要比較真實覆蓋，需要人手對照。
- 沒有「規則 → 測試」的追溯表，無法直接回答「哪條規則未被驗證」。

## 試點做法
- 範圍：第 4.2–4.5 節（證書上限、貸款、賣股、買股），19 條規則、30 個測試（`test_r4_x_y` 命名帶規則編號；表格化的 4.2.1 展開成 5 個人數）。
- 由規則書文字寫測試，只用現有程式碼取得函數名稱來呼叫。
- 一次生成、一次執行，耗時數分鐘，未做 token 精確統計。

## 結果
30 個測試：26 通過、4 失敗。逐個核對：

| 規則 | 測試期望 | 引擎行為 | 判定 |
|---|---|---|---|
| 4.2.3／4.5.8 | 黃區公司股票不計證書上限；已達上限的玩家仍可買 | `buy_share` 達上限即拒絕，沒考慮黃區 | **真實偏差**（可到達）；作者確認按規則 |
| 4.3.1 | 有貸款時不得買股 | 引擎沒有任何貸款檢查 | **缺少防護**（目前可能因貸款功能未實作而不可到達，但規則要求）；作者確認按規則 |
| 4.4.3／4.4.4 | 先按當前價格收款（2 股 ×£100 = £200），再下跌 | 每賣一股後才降價，收 £100 + £90 = £190 | **已確認引擎偏差**（2026-11-21 由作者裁決：按規則，每股收當時價錢，之後才降價）。現有手寫測試 `backend/tests/test_shares.py` 把 190 寫成預期，修正引擎時須一併更新 |
| 4.5.2 | 未有董事時不可買普通股 | 允許購買 | 正常流程中成立公司同時設董事，狀態難以到達；作者確認按規則，引擎缺少明確防護（潛在） |

- 真實問題約 2 至 3 個／30 個測試，其中 1 個（售價）是現有人手測試同樣漏掉甚至固化的。
- 26 個通過的測試與現有手寫測試有大量重疊（19 條規則中只有 1 條和現有引用重合；但行為上多數已被覆蓋）。所以「新增價值」主要是：重新獨立驗證、加上規則編號追溯、並抓到上述差異。

## 結論（初步）
1. 可行：從規則書文字生成帶編號的測試，數分鐘內可得到一批可執行測試，並能自動指出與引擎不一致之處。
2. 有價值的產出不是「全部通過」，而是**失敗清單**：人只需要判定 4 個失敗，而不是逐條玩 19 條規則。
3. 失敗要分類：真實偏差、缺失防護、規則歧義（要人裁決）、測試設定人為。分類本身可由 AI 初判，人最後確認。
4. 追溯表可以自動生成（規則 → 測試 → 結果），解決「哪些規則還未驗證」。

## 限制（必須在論文中誠實說明）
- 只做 4.2–4.5（372 條中的 19 條）；一個遊戲、一個專案、早期版本。
- 測試是由已讀過引擎程式碼的 AI 寫的：雖然只從規則文字推導期望值，但無法排除受實作影響。更嚴格的做法是由沒看過引擎的獨立 agent 生成。
- 4.4.3 已由作者裁決（按規則文字：£200）。其餘三項作者均確認按規則（2026-11-21）：四項測試的期望都正確，引擎需修正或補防護。
- 沒有量度人手驗證所需時間、token 精確用量；也沒有和「人手逐條玩」直接比較。
- 規則書是雙欄 PDF，規則編號抽取不完全；狀態構造靠手寫輔助函數。
- 這驗證的是「規則 → 測試」；契約層（前置後置條件）、問答流程、回饋循環仍未試。

## 下一步
1. 由獨立 agent（看不到引擎）生成其餘章節（5.x 營運回合等）的規則測試，擴大覆蓋並避免污染。
2. 把失敗清單交給你（規則熟悉者）裁決，記錄裁決時間，這是對照「逐條人手測試」的關鍵數字。
3. 自動產生追溯表（規則 → 測試 → 實作節點 → 結果），並接上 Mac 上的 1822 偽代碼圖（需連線）。

測試檔：`claude/code-backup/1822-ch4-pilot-tests.txt`

## 要誠實說明的限制
- **契約由我寫，而我寫契約時已知道哪些測試失敗**，契約裡有幾句間接提示（如「資金從正確來源流動」「其餘證書放入公司庫房」「股價上移」）。這會高估重寫版的得分。更嚴格的做法：契約只由規則書導出，測試另由不看契約的人／agent 撰寫。
- 測試集和契約同源（同一人讀同一份規則），通過測試不等於規則完全正確；`RESULTS.md` 的失敗項只有部分經作者裁決。
- 只試了一個範圍（股票回合 5 個模組）、一次運行，沒有重複、沒有隨機性評估；行數與 token 只是粗略比較。
- 平行化尚未試：這次是一個 agent 寫五個模組。

# 實驗：平行寫（每模組一個 agent）對單一 agent（2026-11-21）

同一份契約、同一個沙盒起點，五個 agent 同時開工，各自只寫一個模組（程式碼在 `verification/regenerated_parallel/`）。

| | 單一 agent（五個模組） | 五個 agent 平行 |
|---|---|---|
| 實際耗時（wall-clock） | 約 203 秒 | 約 126 秒（最慢的 bidding；其餘 26–69 秒） |
| token 總量 | 約 14.2 萬 | 約 47.8 萬（3.4 倍） |
| 工具呼叫 | 16 | 53 |
| 程式行數 | 約 567 | 約 692 |
| 規則測試（116） | 5 失敗（全在範圍外） | 5 失敗（同一批） |
| 原有手寫測試（164） | 13 失敗（9 個為沙盒缺檔，4 個真實差異） | 15 失敗（多 2 個） |

- 規則測試結果相同：重寫範圍內的規則測試全部通過，剩下 5 個失敗屬於未重寫的模組。
- 多出的 2 個失敗（`test_win_a_minor_floats_it_at_phase1_fixed_price`、`test_serialize_state_handles_tuple_keyed_stock_stack`）同一原因：給定的 `round_manager.end_stock_round` 以 `any_sale_this_stock_round` 判斷首輪無人買賣而結束遊戲，但只出價的首輪並未設這個旗標。單一 agent 在 `place_or_move_bid` 內設旗標作變通；平行版的 bidding agent 也在報告中指出這個問題，但沒有變通，因為契約沒有說明，而它只負責自己的模組。→ **跨模組與膠水程式之間的隱含耦合，若契約沒寫明，平行寫就會漏掉。**
- 耗時節省約 38%，但 token 約 3.4 倍：每個 agent 都要重讀契約、規則與給定程式碼（重複上下文）。依賴最重的模組（bidding）決定總耗時，不能再縮短。
- 結論：平行化對「時間」有幫助，對「成本」不利；且要求契約把跨模組的行為（旗標、呼叫順序、誰負責什麼）寫得更清楚。
- 限制：各一次運行；耗時含啟動與讀檔；兩次實驗的契約相同；沒有重複以估計隨機差異。
